# Production Readiness and Security Checklist

This checklist describes what is required before the CMS should serve real production traffic. Presence of code in the repository does not mean that the production environment has been provisioned or tested.

## 1. Dependency and CI baseline

- Root frontend dependencies are pinned to Next.js 15.5.28, React 19.2.7, React DOM 19.2.7 and eslint-config-next 15.5.28. Keep lockfile changes generated by npm, not hand-edited.
- Run `npm ci --legacy-peer-deps`, `npm run type-check`, and `npm run build` in the repository root.
- In `backend/`, run `npm install`, `npm run prisma:generate`, `npm run type-check`, `npm test`, and `npm run build`.
- Do not merge the CMS PR until both GitHub Actions workflows pass on the exact PR head SHA.

## 2. Environment configuration

Frontend:
- `NEXT_PUBLIC_DEFAULT_AUTH=backend`
- `NEXT_PUBLIC_BACKEND_API_URL=https://<your-api-host>/api/v1`
- `NEXT_PUBLIC_SITE_URL=https://<your-canonical-site-host>`

Backend:
- `DATABASE_URL` must point to the production PostgreSQL database and use TLS where supported.
- `JWT_SECRET` must be a randomly generated private secret of at least 32 characters. Set and rotate it using the hosting provider's secret manager.
- `CORS_ORIGINS` must list only the exact deployed frontend origin(s).
- `PUBLIC_SITE_URL` must equal the canonical public site origin.
- `ADMIN_NAME`, `ADMIN_EMAIL`, and `ADMIN_PASSWORD` are needed only when running the seed command; the seed requires a password of at least 12 characters.
- For S3-compatible media storage, set `CMS_MEDIA_STORAGE=s3`, `S3_BUCKET`, `S3_REGION`, `S3_PUBLIC_BASE_URL`, and the appropriate optional endpoint/path-style/credential values in `backend/.env.example`.

Never commit secrets or place private credentials in a `NEXT_PUBLIC_*` variable.

## 3. Database and storage

1. Back up the database before schema migration and test migrations against a staging copy first.
2. Apply production migrations using `npm run prisma:deploy`; do not use `prisma db push` for production schema changes.
3. Seed the first administrator once, from a secure environment, then rotate or replace bootstrap credentials according to operational policy.
4. For serverless hosting, do not rely on a local ephemeral filesystem for uploaded media. Configure a persistent mounted volume or S3-compatible storage and test upload/read/delete behavior.
5. Configure database backups/PITR and rehearse a restore to a separate database.

## 4. Runtime and security boundaries

- Scheduled publication and webhook retries currently use in-process workers. Configure an external cron/durable queue for serverless or multi-instance production so jobs are not skipped or executed concurrently without coordination.
- The public content renderer intentionally renders author-provided rich text/Markdown as text. Do not enable raw HTML rendering until a maintained sanitizer and a strict HTML allowlist are implemented and tested.
- Role grants protect CMS routes, but per-content ownership/team-level authorization and comprehensive security integration tests remain production follow-up work.
- Configure TLS, security headers, rate limits, log retention, error monitoring, alerting, and a documented incident response.
- If a production deployment ran an unpatched Next.js version while public, deploy the patched version before restoring traffic and review/rotate production secrets as appropriate to the exposure window.

## 5. Smoke tests required after deployment

- Sign in with a seeded administrator; confirm USER cannot reach management-only routes.
- Create a page in Persian and English; verify RTL/LTR, localized slugs, SEO metadata, alternate language URLs and public sitemap.
- Verify draft content is not accessible to anonymous callers; publish a page and confirm only its published snapshot is served.
- Upload media, use it from a content block, confirm referenced media cannot be deleted, and verify cleanup after references are removed.
- Submit a valid and invalid public form, confirm throttling, and inspect the submission in the admin UI.
- Send a webhook to a controlled HTTPS endpoint, verify signature/delivery history/retry, and verify private/internal destinations are rejected.
- Run import/export against staging and confirm imports create drafts, report partial failures, and do not assume media binaries are included.
- Check redirects, menus, audit logs, permission grants, backup/restore, keyboard navigation and mobile layouts.

## Scope note

The CMS-specific pages in this branch use real APIs. Legacy e-commerce, CRM, project/task, ticket and other template/demo screens are not all migrated away from Fake Backend. That broader migration needs a separate page-by-page audit, implementation and regression test pass.
